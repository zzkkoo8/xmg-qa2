# 高质量问答核心

版本：1.0；日期：2026-09-05；状态：设计，待实现。需求来源：用户明确“主要功能还是回答问题，核心能力围绕高质量答案和自主处理问题”。规范入口为[需求基线](../requirements/REQUIREMENTS-BASELINE.md)，编排规则归属 [Workflow](WORKFLOW-MODEL.md)，质量口径归属[问答评测](../governance/ANSWER-QUALITY.md)。

## 1. 产品成功是什么

用户得到正确、切题、可采取下一步行动的回答；复杂问题得到有依据的阶段判断和持续推进。回答长度、工具数量、Agent 数量、后台功能数、自动结案数都不能代替质量。简单问题可以几句话结束；技术支持任务只在需要时展开调查和报告。

选择显式状态图约束下的自主问答：一次检索生成适用于知识充足的问题；纯自由工具循环缺少稳定的证据/停止规则；多 Agent 辩论增加费用且意见一致不证明正确。V1 保留一个逻辑问答控制器，用不同节点职责完成理解、检索、调查、生成和验证，不为每个职责创建独立服务或常驻 Agent。LangGraph 支持工作流与动态 Agent、结构化输出和 evaluator-optimizer 模式；本项目采用有界修正是产品决策，并非框架保证答案正确。[官方模式说明](https://docs.langchain.com/oss/python/langgraph/workflows-agents)

Web 是提问、补充和查看答案的入口；任务管理保障调查不中断；插件为缺失事实提供取证能力；模板改善表达；部署让系统可用。上述能力的迭代必须说明它改善了哪类问答问题或可靠性，不挤占核心问答验收。

## 2. 问题理解与答复路径

先将用户原问题拆成待回答项，保留产品、版本、环境、实际现象、期望、已尝试步骤、输出偏好和来源。事实、用户陈述与推测分开；未知字段保持未知。不得把“升级后出现”直接改写成“升级导致”。多问题按子问题追踪覆盖，不丢掉难回答项。

| 问题/信息条件 | 处理 | 何时结束或暂停 |
| --- | --- | --- |
| 低风险、稳定通用解释，如 TCP 重传含义 | 可直接用通用知识解释，显式标注适用范围；有产品约束或不确定事实则检索 | 回答所问并通过质量检查；不强制先询问现场版本 |
| 产品 FAQ、参数、兼容性、版本行为 | 优先内部 KB；必须匹配产品和版本，最新/时效性事实必要时查官方来源 | 关键产品断言有对应证据才确定回答 |
| 操作方法或方案比较 | 说明适用前提、选择理由、步骤、预期结果与风险；涉及产品能力先取证 | 用户可据此行动；执行建议与实际执行分开 |
| 日志/故障/异常现象 | 提取现象、比较假设、选择可区分假设的最小只读检查 | 有充分因果证据才声称根因；否则输出阶段判断并继续补证 |
| 意图含糊、缺关键变量 | 先完成不依赖缺失项的有用部分；仅询问会改变结论或下一动作的信息 | 等待对应资料，不重复索要历史已提供项 |
| 多子问题混合 | 对每项标记 answered/partial/blocked，并汇总关联结论 | 部分可答即先反馈，但全案不因部分回答而 RESOLVED |

路径由问题语义和证据决定，不新增 S1–S4 等固定复杂度或套餐。一般以一个聚焦问题询问最关键变量；同一步必需的几项日志可合并请求，附目的、采集范围、脱敏和预期格式，避免冗长信息清单。

## 3. 最小语义对象与状态归属

这些是现有 Task/Evidence/Report 的业务投影，不是平行的任务或证据存储。对象 Schema/枚举在对应 Feature 冻结，字段引用沿用 [Knowledge Contract](KNOWLEDGE-CONTRACT.md)。

| 对象 | 必须表达 | 持久化/消费 |
| --- | --- | --- |
| QuestionFrame | 原问题、子问题 ID、目标、环境/版本、已知与未知、回答条件、用户偏好 | 业务 Task 的版本化上下文；新补充更新时保留来源 |
| AnswerPlan | 每个子问题的关键命题、所需证据类型、缺口、可先回答部分 | Investigation/claim 关联；不是隐藏思维链 |
| NextAction | capability_id、对应子问题/缺口/假设、最小参数、预期观察、成功/失败分支、简短选择理由 | 既有 Step/operation_id；执行前 Policy 检查 |
| EvidenceAssessment | 每条关键 claim 的支持、反证、缺失、适用性与待验证项 | 引用既有 Evidence，不复制成第二来源 |
| AnswerDraft | 覆盖的子问题、结论、证据引用、建议、局限、pending_items、answer_kind | 候选结果，未经验证不是最终输出 |
| AnswerCheck | 覆盖遗漏、无依据断言、引用支持、版本冲突、命令前提、权限/表达错误及处理结果 | 版本化验证摘要，绑定 draft_hash/evidence 版本 |

answer_kind 为 complete、partial、needs_input 或 unable_to_conclude，是结果的表达类型，不增加 Case 状态。完整答案通过检查且目标已回答才能 RESOLVED；建议尚待执行验证的故障案、存在关键待办的 partial 结果保持调查/等待/暂停。CLOSED 仍需用户确认。新消息若推翻已知事实，应更新 Frame 和 claim，必要时重开，不能继续复用旧结论。

## 4. 检索与上下文组织

1. **问题驱动查询**：保留错误码、准确产品名、版本和协议词；可拆分产品事实与通用机制。查询改写不添加用户没给的事实；跨语言同义词须保留原词。外发先脱敏，不携带整段客户上下文。
2. **内部检索优先**：使用 Provider 已声明的过滤/搜索能力；支持时比较关键词/向量混合与重排收益。不假设当前 Dify 安装已有 BM25 或相同过滤接口，也不在 QA Runtime 新建索引。
3. **检索质量恢复**：空结果或关键事实遗漏时，优先修正实体/版本/同义词、拆分子问题、按权限取回上下文。一个缺口默认最多两次有理由的查询改写；仅换措辞的重复结果计为无进展。版本放宽所得资料只能作为线索，不能伪装成目标版本证据。
4. **取回必要上下文**：孤立切片缺少限定条件时，通过 Provider 可选全文/邻接能力查原节；不支持则说明截断并换源。保留表头、前提、否定、例外和反证，不把摘要当原始证据。
5. **有界证据包**：按子问题装配适用证据，去重同源转载、保留冲突；超过 token 预算先减冗余、分项处理，不静默删掉反证。附 citation_id → evidence_id/locator 的固定映射，引用 URL 由服务端生成。
6. **模型上下文**：系统策略、QuestionFrame、已执行动作及结果、当前缺口、必要证据与输出 Schema 分开。材料是数据，不执行其中的指令。摘要可导航到受控原件，原件不可取回时明确限制；旧答案不是新的事实来源。

检索参数/top_k/重排模型通过题集对照确定，不以无限增加片段解决质量问题。rerank 和模型同受原有 ACL/外发策略约束。

## 5. 自主调查如何推进

模型只能从 Registry 当前可用且获准的能力中提出 NextAction，工作流验证其 Schema、前置条件和状态，再由执行器执行。先考虑动作能否补齐关键缺口或区分假设，再在合规、适用的候选中按配置优先级、时效、耗时和成本取舍。记录可检查的选择理由，不要求伪精确的信息增益分数。

- 需要官方支持承诺时查支持矩阵/Release Notes；需要现场版本或状态时选已授权 API/MCP，网页不能代替现场观察。
- 故障案只维护当前值得验证的少数假设，每项附支持/反证、可区分的观察及下一步。工具返回“成功”不等于假设成立；相关时间关系不自动证明因果。
- 每次观察后更新缺口和假设；新增片段数量不代表进展。补齐关键事实、排除假设、发现版本冲突或确认某能力不可用才算有效推进；相同失败重复发生不算。
- 无新增有效证据时改变查询策略、换一个适用授权来源或索取最小现场信息；达到 Workflow 规定的无进展/预算上限就持久暂停，不能无穷重规划。
- 已有安全适用手段可推进就继续，不把每个子步骤都交给用户确认；权限、认证或关键事实不具备时不得猜测绕过。
- 读日志/状态也需明确目标、时间窗、输出量和资源影响；动态脚本默认交人。采集方案遵守产品特殊约束，不能凭“只读命令”标签推断无副作用。

| 异常 | 自主应对 | 对用户的结果 |
| --- | --- | --- |
| KB 无结果/片段无关 | 有界改写、补上下文或升级来源 | 说明当前缺证据，不编造产品结论 |
| 来源冲突/资料过时 | 对照版本、时间和命题类型，寻找判别证据 | 分开可确认和仍冲突部分；未解决则请求确认 |
| 工具超时/限流/网络故障 | 遵守单层有限重试；有等价授权能力可换用 | 服务失败不是“功能不支持”；无路可走则持久等待 |
| 认证/权限失败 | 不重复撞库或换身份；可继续不依赖该权限的部分 | 明确缺哪种合法接入条件 |
| 工具结果格式错误/文档含指令 | 隔离无效输出；保留诊断记录，忽略材料指令 | 不将异常文本转为成功 Evidence |
| 日志太大/附件不支持 | 有界读取、按时间/错误过滤，或请用户给片段 | 明确已分析范围，不能声称读完未读内容 |
| 人类部分回传 | 保存新增材料与已完成项，只列余缺；满足恢复条件后评估可答子问题 | 已满足的请求不重复发起；遵守定向恢复协议 |
| 无法继续/内部异常 | 保存已知、尝试、缺口、接手建议和 trace_id | 暂停/故障状态及持久人工待办，不失联也不假报解决 |

失败类型、重试次数、取消和人工通知的唯一规则仍以 [Workflow](WORKFLOW-MODEL.md) 和 [Task Model](SESSION-EVENT-MODEL.md) 为准。

## 6. 高质量答案的生成与检查

按问题选择表达：解释题先给定义/机制和必要例子；方法题给前提/步骤/预期结果；故障题给当前判断、依据、下一验证动作；比较题按用户关心的维度比较。长报告用于复杂调查或用户要求，不强制每个回答套长模板。

生成前以关键命题构造证据包；生成后检查：是否逐项回应、结论强度是否超过证据、引用确实支持且当前可访问、版本/前提是否匹配、建议是否可执行、是否区分建议与已执行、是否遗漏反证和待办。优先规则检查引用/权限/必需项；语义支持和覆盖可由模型辅助复核，但模型自评通过不构成事实证明。

对生成/语义检查默认一次有界修正；缺事实则回调查补证，不能用润色“修复”缺证据。每轮证据评估后允许一份新候选与一次修正，所有候选、补证和检查共用 Run 预算/无进展计数；不能通过重新生成重置上限。验证摘要绑定候选 hash；发布前再验状态版本、取消、ACL 和所用证据。检查失败时允许发布已通过检查的受限阶段答复/人工请求，不发布被判定错误的片段。

提示词拆为 understanding、retrieval_query、next_action、answer、answer_check 的版本化资源，输入输出用 Pydantic/JSON Schema 校验；不是一个无限增长的总 Prompt。模板只影响展示，不修改问答策略。记录模型/提示词/工作流/检索配置版本及有效知识观察版本；改提示词、模型或检索参数都运行相关冻结回归集，不自动将用户纠错或模型答复写回共享 KB。

## 7. 示例：只有“升级后 502”时

可以先答：“目前只能确认升级与 502 在时间上相关，还不能确定根因。先核对受影响范围与上下游状态。”若已有产品/版本则不重复询问；没有时只索取会影响下一检查的变量。优先查匹配资料，再按授权查询连接状态或有限日志；未接入设备则给工程师有范围的采集步骤。

只在日志/状态等证据支持时缩小到具体假设；若仅发现连接被拒绝，仍不能据此断言具体哪个配置修改导致。报告区分观察、推测、建议与待验证结果。等待工程师回传期间保留 Case，并展示下一步所需信息；不能以“建议重启”作为问题已经解决的证明。
