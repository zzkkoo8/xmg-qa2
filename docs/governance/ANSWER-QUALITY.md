# 问答质量与回归评测

版本：1.0；日期：2026-09-05；状态：验收设计，未运行评测。需求基线第 5 节为总目标；本文细化口径。核心行为见 [QA Core](../architecture/QA-CORE.md)。数值是本项目初始验收目标，不是行业排名或已经达到的成绩。

## 1. 什么算一份好答案

| 维度 | 工程师检查 | 典型失败 |
| --- | --- | --- |
| 正确与适用 | 必需事实正确，产品/版本/环境匹配，因果表述有依据 | 把可运行当官方支持，把相关性当根因 |
| 切题与完整 | 回应全部子问题，给当前可答部分，明确剩余缺口 | 避答难点、长篇通用介绍掩盖未回答 |
| 证据可靠 | 引用真实可访问且支持相应命题；保留反证与时间 | 有引用但不支持，引用错误版本或模型虚构 URL |
| 可执行 | 步骤有适用前提、目的、合理范围和预期观察 | 不分环境给命令，声称未运行步骤已成功 |
| 不确定性恰当 | 已证实、推测、待验证清楚；必要时求助 | 过度确定，或简单可答问题也转人工 |
| 自主处理 | 下一动作补齐缺口，有进展则继续，失败能换适用路径 | 重复同一查询、无意义工具调用、过早放弃 |
| 表达 | 结论靠前、必要细节够用，引用靠近主张 | 短题长报表、堆工具日志和内部推理 |

不强制所有句子带引用。低风险通用解释可免外部引用，但仍评事实正确性；产品承诺、现场事实、确定根因必须有适用证据。人工请求质量包括是否必要、是否只索取缺失项、回传后是否实际推进。

## 2. 题集与对照

- 先建不少于 20 条合成/脱敏的开发场景用于首个 Feature 的路由、缺口、检查和恢复测试；Fake 输出只验证控制行为，不用于证明模型答案质量。
- 真实 KB/模型 Feature 起，建立独立开发集与不少于 100 个工程师标注的冻结回归案例（冻结集本身不少于 100，开发集另计）。覆盖产品 FAQ、通用解释、操作步骤、版本冲突、故障/日志、多子问题、资料不足、工具失败、越权/注入、多轮恢复，每类至少 10 例；主类不重复计数，可另加交叉标签。
- 同一事故、原题改写或近重复不能跨开发/冻结集泄漏。保存产品/版本/日期、授权 Evidence 快照或 observation/hash、必需事实与关键命题、允许局限、合理下一动作及终止条件。脱敏材料与评测产物保持相应 ACL，公开仓库只放合成或明确可公开案例。
- 在同一模型、资料和运行环境比较：一次检索生成的基线 vs 本项目有界问答；单独改变检索/重排、Prompt、模型或动作策略做对照。动态现场用可重放观察测行为，另跑真实集成，不能把回放称为现场成功。
- 多轮案例提供随动作返回的观察/人类输入以及可接受轨迹，不强制唯一工具顺序；评是否解决缺口、避免越权与重复。真实 endpoint 或相关题类缺失时标记未验收，不能删掉分母宣称全 V1 通过。

## 3. 发布指标口径

| 指标 | 分母与判定 | 初始门槛 |
| --- | --- | --- |
| 关键断言引用覆盖 | 所有已输出且需要外部证据的关键断言；有真实定位引用的数量/总量 | ≥95% |
| 证据支持准确 | 已引用的关键断言；引用在适用版本/环境内足以支持的数量/总量 | ≥90% |
| 必需事实覆盖 | 可回答案例标注的必需事实；正确回答的数量/总量，遗漏计失败 | ≥90% |
| 可回答案例合格率 | 标注为现有能力/资料可答的案例；必需关键事实正确完整、步骤可用、无重大错误且检查通过的案例/总量 | ≥90%；同时逐类报告 |
| 正确求助/受限答复 | 对应动作的精确率 TP/(TP+FP) 与召回率 TP/(TP+FN)，分别计算必要澄清、转人工、拒绝越权/无法断言 | 精确率、召回率各 ≥90% |
| 自主调查成功 | 标注在授权资料/能力下可推进至目标的复杂案例；完成目标且轨迹符合约束的案例/总量 | ≥90%；正确转人工不能充作已解决 |
| 安全与严重失真 | 确定性安全/隔离集；生产写、越权、泄密、错误恢复、伪造执行/来源、无证据确定根因等逐项计数 | 0 次，任一触发阻断 |
| 延迟与费用 | 延续需求 SLO；每题记录完整响应 p50/p95、模型/检索/工具调用、重试、人工往返及费用 | 简单知识回答既有 p95≤30秒目标；费用报告实值，初次实测再冻结预算 |

分母为零标记 N/A 和缺覆盖，不记 100%；必要行为缺样本不能通过该门禁。可回答题被过早转人工记为未合格；应求助题直接编造回答记召回失败。关键断言在评测时由标注/复核识别，不允许生成器通过省略 claim 标签逃避统计。所有子问题计入覆盖，不能挑容易回答的部分提高分数。

人工对可回答合格率按上述事实/行动标准判定；严重错误清单优先于总分。报告样本数、失败案例与比例，不将 10 条子类样本的高分宣传成稳定泛化能力。重复运行保持冻结样本与配置；模型波动报告分布，不挑最好的一次。首次门槛不足只能记录失败或在看到下一冻结集前经显式需求变更调整，不事后调低阈值掩盖回归。

## 4. 工具与人工复核

pytest 验证确定性状态、权限、Schema、停止与恢复；实施阶段以轻量评测脚本输出逐例 JSON/表格与聚合报告即可，V1 不新建评测平台。Ragas 为可选离线依赖：faithfulness 测回答对提供上下文的支持关系，不能证明上下文本身真实；response relevancy 测切题，不验证事实正确性。因此两者只用于定位问题，不能替代上述工程师标注门禁。[Faithfulness](https://docs.ragas.io/en/stable/concepts/metrics/available_metrics/faithfulness/) · [Response Relevancy](https://docs.ragas.io/en/stable/concepts/metrics/available_metrics/answer_relevance/)

LLM judge 固定模型/Prompt/数据范围；用人工标注校准，防评测材料指令注入。至少复核全部严重/不一致案例及各类通过案例的 20%（向上取整），发布所用“工程师合格率”需工程师逐例判定，不把抽样替代完整标注。人类分歧保留说明并裁决；生成模型给自身打高分不能直接通过。

## 5. 迭代与交付

首个 Feature 建立场景 Schema、合成控制测试与逐例结果结构；真实 KB/模型 Feature 交付第一份质量基线，能力升级 Feature 加入行动轨迹评测。早期基线报告保留尚未集成题类并标记未验收，可完成当阶段范围，但不能宣称全 V1 质量门禁通过。Chat/Admin 和分发继续按既有路线完成，最终联合验收重跑完整集。模型、提示词、检索配置、工作流或模板语义变动都跑相应回归，涉及共享判断则跑全冻结集。

失败归因到理解、检索、证据裁决、能力选择、生成、验证或展示；只修失败所在层再比较。用户纠错先成为受控评测候选，经工程师核实后提交知识维护待办；不自动用模型答案训练自身或污染共享 KB。完整运行记录包括版本、数据观察、输入范围、期望/实际结果、轨迹、判定与费用，未执行项写未执行。
